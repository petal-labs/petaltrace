## Summary

Wired the HTTP API server into the `petaltrace serve` command and created a new `petaltrace mcp` subcommand for running the MCP server. The serve command now starts both the OTLP collector and the HTTP API server. The MCP server is a separate command that uses stdio transport for integration with MCP clients like Claude Code.

## Motivation

Phase 8.5 completes the daemon integration by connecting all implemented components:
1. The OTLP collector for receiving traces
2. The HTTP API server for querying traces, running diffs, and triggering replays
3. The MCP server (as a separate command) for agent-based trace inspection

This enables the full observability workflow where traces can be collected, stored, queried, compared, and replayed through both HTTP APIs and MCP tools.

## What Changed

### New Additions

**cmd/petaltrace/mcp.go** — New MCP subcommand
- `petaltrace mcp` command for running the MCP server
- Uses stdio transport (stdin/stdout) for MCP protocol
- Initializes diff engine and replay engine
- Handles graceful shutdown on SIGINT/SIGTERM
- Logs to stderr to avoid interfering with MCP protocol on stdout

### Modifications

**cmd/petaltrace/serve.go** — Updated serve command
- Added import for `api` package
- After starting the collector, now also starts the API server
- API server binds to configured `server.host` and `server.port` (default `0.0.0.0:8090`)
- Graceful shutdown now stops both API server and collector
- Improved logging to show both API and collector addresses

N/A

## Technical Specification

### Serve Command Startup Sequence

```
1. Load configuration from petaltrace.yaml or --config flag
2. Initialize logger
3. Create data directory if needed
4. Initialize SQLite store
5. Load pricing table
6. Create and start OTLP collector (ports 4317/4318)
7. Create and start HTTP API server (port 8090)
8. Wait for shutdown signal
9. Stop API server
10. Stop collector
```

### MCP Command Startup Sequence

```
1. Load configuration
2. Initialize logger (to stderr)
3. Initialize SQLite store
4. Load pricing table
5. Create diff engine
6. Create replay engine
7. Create MCP server with stdin/stdout
8. Run MCP server (blocks until stdin closes)
9. Graceful shutdown
```

### Server Addresses

| Service | Default Port | Configurable Via |
|---------|--------------|------------------|
| HTTP API | 8090 | `server.port` |
| OTLP/gRPC | 4317 | `collector.otlp_grpc_port` |
| OTLP/HTTP | 4318 | `collector.otlp_http_port` |

```bash
# Start with defaults

# Start with custom config
petaltrace serve --config /path/to/petaltrace.yaml
```

## Integration Notes

The serve command now provides a complete observability daemon:

1. **PetalFlow Integration** — PetalFlow can send OTLP traces to ports 4317 (gRPC) or 4318 (HTTP)
2. **HTTP API** — Query traces, compute diffs, trigger replays via REST endpoints
3. **MCP Tools** — Agents can use `petaltrace mcp` for self-reflective trace inspection
4. **UI** — The API server structure is ready for embedded UI (Phase 2 implementation)

The MCP server is intentionally a separate command because:
- MCP uses stdio transport requiring exclusive stdin/stdout access
- MCP clients spawn the server as a subprocess
- Separation allows running multiple instances or running without the daemon
