## Summary

PetalTrace 1.0 now declares PetalFlow v1.2.0 as its minimum supported runtime version. The PetalFlow v1.2.0 candidate adds compatibility routes for live and hybrid replay, while PetalTrace recognizes the current PetalFlow OTLP attribute names and verifies both replay endpoints plus trace ingestion in a process-level CI test.

## Motivation

PetalTrace had no PetalFlow module dependency to version-pin, but its replay engine depended on HTTP routes that were absent from the latest published PetalFlow v1.1.0. Its collector also expected older dot-separated attribute names while PetalFlow v1 emits underscore-separated names and current GenAI semantic conventions. This change defines and tests the runtime contract instead of relying on stale, unverified assumptions.

## What Changed

### New Additions

- `integration/petalflow_contract_test.go` launches a PetalFlow candidate binary, invokes both replay routes, sends its OTLP/HTTP traces through a real PetalTrace collector, and verifies run metadata, snapshots, node spans, and mocked tool outputs.
- `.github/workflows/petalflow-contract.yml` builds the pinned PetalFlow v1.2.0 candidate source and runs the process-level contract test on pull requests and main pushes.
- `replay/hybrid_test.go` verifies captured tool outputs are keyed by PetalFlow tool-node ID.

### Modifications

- `collector/correlator.go` accepts PetalFlow v1 attribute names, parses JSON snapshots transported as strings, and merges root metadata if child spans arrive first.
- `collector/classifier.go` recognizes PetalFlow v1 node, tool, edge, GenAI provider, and content attributes.
- `replay/mocked.go` and `replay/hybrid.go` resolve hybrid fixtures using workflow tool-node IDs, with legacy attribute fallbacks.
- PetalFlow's `/api/execute` and `/api/execute/hybrid` compatibility routes are implemented in the paired PetalFlow change. They are added in PetalFlow v1.2.0; PetalFlow v1.1.0 does not provide these routes.
- Full PetalTrace capture exports graph, input, config, and tool-output snapshots; lower capture modes remain metadata/content-policy controlled.
- PetalTrace CLI, API, and MCP replay engines send `PETALFLOW_API_TOKEN` as a bearer token. `petalflow.url` selects the endpoint, and `--petalflow-url` can override it in CLI replay commands.

### Removals

N/A. No existing PetalTrace routes or stored data fields were removed.

## Technical Specification

### Data Schemas / Types

The integration test uses the PetalFlow v1.2.0 replay request shape:

```json
{
  "workflow_id": "workflow-123",
  "workflow_name": "support-agent",
  "graph": {"id": "workflow-123", "schema_version": "v1", "kind": "graph", "nodes": [], "edges": []},
  "input": {"question": "Where is my order?"},
  "config": {},
  "parent_run_id": "source-run-id",
  "tags": {"replay_mode": "hybrid"},
  "trigger_source": "petaltrace-hybrid-replay",
  "tool_mock_mode": "all",
  "mocked_tools": {"lookup_order": {"status": "shipped"}}
}
```

PetalFlow v1 OTLP attributes include `petalflow.run_id`, `petalflow.workflow_id`, `petalflow.node_id`, `petalflow.node_kind`, `petalflow.edge.source_node`, `gen_ai.provider.name`, and `petalflow.llm.completion`. Under full capture, graph/input/config snapshots use `petalflow.graph_definition`, `petalflow.input_snapshot`, and `petalflow.config_snapshot`; tool outputs use `petalflow.tool.outputs`.

### API Endpoints

- PetalFlow `POST /api/execute` executes a graph and returns `{"run_id":"...","status":"completed"}`.
- PetalFlow `POST /api/execute/hybrid` accepts the same request plus `tool_mock_mode` (`all` or `none`) and `mocked_tools`, keyed by graph tool-node ID.
- Both routes use the daemon's normal authentication and body-size limits. `all` mode rejects missing tool fixtures rather than invoking tools live. PetalTrace sends an `Authorization: Bearer <token>` header when `PETALFLOW_API_TOKEN` is set.

### CLI Interface

The existing `petaltrace replay` `--petalflow-url` flag now overrides `petalflow.url`. When omitted, the command uses the configured URL (default `http://localhost:8080`). Replay HTTP requests use the bearer token in `PETALFLOW_API_TOKEN`.

### Go Package API

`replay.EngineConfig`, `replay.LiveReplayerConfig`, and `replay.HybridReplayerConfig` add `PetalFlowToken string`. When non-empty, live and hybrid replay requests send `Authorization: Bearer <token>`.

```go
type EngineConfig struct {
	Store          store.TraceStore
	PetalFlowURL   string
	PetalFlowToken string
	Logger         *slog.Logger
}

type LiveReplayerConfig struct {
	Store          store.TraceStore
	PetalFlowURL   string
	PetalFlowToken string
	RequestTimeout time.Duration
}

type HybridReplayerConfig struct {
	Store          store.TraceStore
	PetalFlowURL   string
	PetalFlowToken string
	RequestTimeout time.Duration
}
```

`api.ServerConfig` adds `PetalFlowURL` and `PetalFlowToken` so API-triggered replay requests use the configured endpoint and bearer credentials.

### Configuration

- `petalflow.url` (`string`, optional, default `http://localhost:8080`) selects the PetalFlow daemon URL. It is read from `petaltrace.yaml` or `PETALTRACE_PETALFLOW_URL`; CLI `--petalflow-url` overrides it.
- `PETALFLOW_API_TOKEN` (environment variable) supplies the bearer token required by `petalflow serve`. PetalTrace sends it as `Authorization: Bearer ...` for live/hybrid replay requests.
- `observability.petaltrace.capture_mode` remains a PetalFlow setting. Use `full` to emit graph/input/config snapshots and tool outputs needed for PetalTrace replay; lower levels do not include snapshots.

The PetalTrace configuration type adds:

```go
type PetalFlowConfig struct {
	URL string `mapstructure:"url"`
}
```

## Usage Examples

### Example: Verify the supported PetalFlow runtime contract

```sh
export PETALFLOW_API_TOKEN='your-petalflow-token'
petaltrace replay "$SOURCE_RUN_ID" --mode hybrid --petalflow-url http://localhost:8080
```

The CLI reads `petalflow.url` from configuration unless `--petalflow-url` is supplied. The token is read from `PETALFLOW_API_TOKEN`.

PetalFlow v1.1.0 is not a supported PetalTrace 1.0 runtime: its daemon does not register `/api/execute` or `/api/execute/hybrid`.

## Integration Notes

The runtime relationship is HTTP/OTLP; PetalTrace still has no PetalFlow, Iris, or Cortex Go module dependency. PetalFlow v1.2.0 is the minimum supported runtime and exposes the two replay routes. PetalFlow's full capture mode sends graph/input/config snapshots and tool outputs through OTLP; the collector supports the v1 attribute spellings while retaining aliases for existing traces.

## Breaking Changes & Migration

None to PetalTrace's public API. Deployments using PetalTrace live or hybrid replay must run PetalFlow v1.2.0 or newer; PetalFlow v1.1.0 lacks the replay routes. No Go dependency version update is applicable for Iris or Cortex because neither is a PetalTrace module dependency.

## Deferred / Out of Scope

- The CI job pins PetalFlow candidate commit `928097c8ed85fbce5ee8468cc65a249d3e7c9812` until the official v1.2.0 release is published. The pinned source commit is the behavior tested by this change.
- Provider-backed LLM execution is not part of the integration test; its graph has no live provider call, so CI needs no provider credentials.
