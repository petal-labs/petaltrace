## Summary

Created the project's first `CHANGELOG.md` (Keep a Changelog format) documenting the v0.1.0 initial release, and added a `VERSION` file declaring `0.1.0` so the documentation pipeline and release tooling have a single declared version.

## Motivation

Tagging the initial v0.1.0 release requires a user-facing changelog. A `VERSION` file also resolves the previously undeclared version (`go.mod` carries no module version and no version file existed), which the `/docs/changes/` convention reads for front-matter versioning.

## What Changed

### New Additions

- `CHANGELOG.md` — Keep a Changelog format with an `Unreleased` section and a `[0.1.0] - 2026-11-19` section covering all features shipped to date (collector, storage, CLI, HTTP API, UI, replay, diff, MCP, PetalFlow runtime contract), the bug fixes merged through v0.1.0, and the release platform (tag-triggered multi-platform binaries + checksums).
- `VERSION` — single line containing `0.1.0`. It is not consumed by the build (the Makefile and release workflow derive the binary version from `git describe --tags` / `GITHUB_REF_NAME` via ldflags); it exists as the declared project version for tooling and documentation.

- The Makefile's `VERSION ?= $(shell git describe --tags ...)` and the release workflow's `VERSION=${GITHUB_REF_NAME}` remain the authoritative build-time version sources; the `VERSION` file does not affect binaries.

- The changelog's compare/tag links target `github.com/petal-labs/petaltrace` releases.
