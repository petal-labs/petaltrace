## Summary

`petaltrace gc` previously listed runs with a single oversized `ListRuns` call (`Limit: 10000`). Store backends clamp `Limit` to 1,000 and fall back to their default page size of 50 for anything larger, so GC only ever evaluated the newest page of runs and silently left older eligible runs in the database. GC now follows the store's cursor across every result page until no cursor remains, deleting (or reporting, in dry-run) every eligible run exactly once.

## Motivation

GitHub issue #6 ([P1] Make garbage collection traverse every run page). `runGC` ignored the cursor returned by `ListRuns`, so with more than one page of runs the command reported success while leaving eligible runs on later pages untouched. Retention-based garbage collection is the primary mechanism for bounding database growth, so under-counting deletions defeats its purpose.

## What Changed

### New Additions

- `gcPageSize` variable in `cmd/petaltrace/gc.go` (default `1000`): the number of runs requested per `ListRuns` page during GC. It is a variable (not a constant) so tests can force multi-page traversal with a small page size.

### Modifications

- `runGC` in `cmd/petaltrace/gc.go` now runs a cursor-driven loop over `ListRuns` pages instead of a single call. Before:

  ```go
  runs, _, err := traceStore.ListRuns(ctx, store.ListRunsOptions{Limit: 10000})
  ```

  After:

  ```go
  var toDelete []store.Run
  cursor := ""
  for {
      runs, nextCursor, err := traceStore.ListRuns(ctx, store.ListRunsOptions{
          Limit:  gcPageSize,
          Cursor: cursor,
          SortBy: "id",
      })
      if err != nil {
          return fmt.Errorf("listing runs: %w", err)
      }
      // ... per-run retention/starred filtering appended to toDelete ...
      if nextCursor == "" || nextCursor == cursor {
          break
      }
      cursor = nextCursor
  }
  ```

- `buildRunsOrderByClause` in `store/sqlite_runs.go` (shared with the PostgreSQL backend in `store/postgres.go`) now whitelists `"id"` as a sort column. GC passes `SortBy: "id"` so pagination is coherent with the store's id-based cursor (`id < cursor`): every run appears on exactly one page, regardless of how `started_at` interleaves with id order. Sorting by the default column (`started_at`) while paging on `id < cursor` can both repeat and skip runs whenever id order does not match started_at order.

### Removals

None.

## Technical Specification

### Data Schemas / Types

N/A — no schema or type changes. `ListRunsOptions` (in `store/models.go`) is unchanged; the fix only changes which field values `runGC` passes.

### API Endpoints

N/A — daemon API is untouched.

### CLI Interface

`petaltrace gc` keeps its existing flags (`--retain`, `--dry-run`, `--include-starred`, `--verbose`) and output format. Behavior changes only in that all pages of eligible runs are now considered. No new flags.

### Go Package API

- No exported signatures changed. `store.RunStore.ListRuns(ctx, opts ListRunsOptions) ([]Run, string, error)` is unchanged; `runGC` now consumes the previously-ignored second return value (the cursor).
- New package-level variable `gcPageSize int` (default 1000) in `package petaltrace` (`cmd/petaltrace`), not exported beyond the binary's package.

### Configuration

N/A — no new or changed config fields. Retention comes from `retention.default` or `--retain` exactly as before.

## Usage Examples

### Example: multi-page collection (behavior before vs after)

With 2,500 runs, all older than the retention period, on SQLite:

```bash
# Before: fetched default page of 50 (10000 clamps out of range),
# deleted at most 50 runs, reported success.
petaltrace gc
#   Found 50 runs to delete.
#   Deleted: 50 runs

# After: pages through all 2,500 runs.
petaltrace gc
#   Found 2500 runs to delete.
#   Deleted: 2500 runs
```

### Example: dry-run across pages

```bash
petaltrace gc --dry-run --retain 30d
# Garbage Collection
# ==================
# Retention period: 30 days
# ...
# Found 412 runs to delete.
#
# Runs that would be deleted:
#   ✓  01HQ...  my-workflow  started 2026-09-01
#   ...
# Dry run complete. Use without --dry-run to delete.
```

### Error case: listing failure mid-traversal

If any page fails, `runGC` returns `listing runs: <cause>` and deletes nothing (deletion happens only after the full traversal completes), so a partial failure cannot leave the operator with a misleading partial-deletion report.

## Integration Notes

- `ListRuns` cursor semantics (`id < cursor`, per page's last row id) are unchanged; only a new allowed `SortBy` value (`"id"`) was added to the shared whitelist used by both SQLite (`store/sqlite_runs.go`) and PostgreSQL (`store/postgres.go`) backends. Other callers (API `/api/runs`, MCP tools, `cost`, `stats`, `runs` commands) are unaffected because they do not pass `SortBy: "id"`.
- The daemon API and web UI still paginate on the default `started_at` sort with an id-based cursor, which has the same order/cursor mismatch. Fixing that coherently for all consumers is deferred (see below); GC sidesteps it by pinning its own sort to `id`.
- Starred-run preservation and `--include-starred` semantics are unchanged and are covered on every traversed page.

## Breaking Changes & Migration

None. CLI flags, output format, config, and store APIs are unchanged. The only observable behavior change is that GC now deletes (or lists in dry-run) eligible runs from *all* pages, which is the intended fix.

## Deferred / Out of Scope

- Generalizing coherent keyset pagination across all `ListRuns` consumers (e.g., making the cursor sort-aware or adding `id` cursors for every sort column). The daemon API/UI pagination mismatch is out of scope for this issue.
- Server-side (SQL-level) deletion of eligible runs in a single statement; deletion remains per-run via `DeleteRun` so `--verbose` output and per-run error accounting stay identical.
