## Summary

The CLI `petaltrace cost summary`, the API `GET /api/cost/summary`, and the API `GET /api/cost/timeseries` each listed runs with a single oversized `ListRuns` call (`Limit: 10000`) and discarded the returned cursor. Store backends clamp `Limit` to 1,000 and fall back to a default page of 50 for anything larger, so totals, token breakdowns, groupings, and time buckets silently omitted every matching run beyond the first page. All three now page through the full result set.

## Motivation

GitHub issue #7 ([P1] Aggregate cost reports across all matching run pages). Same root cause as issue #6 (GC page traversal): `ListRuns` caps a single call, so any caller that requests "all runs" with an oversized limit and ignores the cursor sees only the newest page. For cost reports this under-counts money and tokens, which is worse than cosmetic — the numbers drive billing decisions.

## What Changed

### New Additions

- `listAllCostRuns(ctx, st store.TraceStore, opts store.ListRunsOptions) ([]store.Run, error)` in `api/cost.go`: shared pagination helper that follows the `ListRuns` cursor until none remains and returns all matching runs.
- `costRunsPageSize` package variable (default `1000`) in both `api` and `cmd/petaltrace`: runs requested per `ListRuns` page. It is a variable (not a constant) so tests can force multi-page traversal with small pages.

### Modifications

- `handleCostSummary` (`api/cost.go`) and `handleCostTimeseries` (`api/cost.go`) replaced their single `ListRuns(ctx, opts{Limit: 10000})` call with `listAllCostRuns(ctx, s.store, opts)`. The `Since`/`Until` filters in `opts` are unchanged and are applied by the store to every page.
- `runCostSummary` (`cmd/petaltrace/cost.go`) replaced its single call with an inline cursor loop requesting `costRunsPageSize` runs per page, sorted by `id`, until no cursor remains. The `--since` window is unchanged and applied per page.
- All three callers pass `SortBy: "id"` so pagination is coherent with the store's id-based cursor (`id < cursor`): every run appears on exactly one page regardless of how `started_at` interleaves with id order. (Same rationale as the GC fix in issue #6; `"id"` was already whitelisted as a sort column in that change.)

### Removals

None.

## Technical Specification

### Data Schemas / Types

N/A — no schema or type changes. `ListRunsOptions` is unchanged.

### API Endpoints

- `GET /api/cost/summary` and `GET /api/cost/timeseries` keep their exact request/response shapes. The only behavioral change is that aggregation covers all matching runs, not just the first page. Pagination is internal to the handlers; responses are unchanged and still unpaginated aggregates.
- A listing failure on any page now surfaces as `500 failed to list runs` (same as before), and no partial response is produced.

### CLI Interface

`petaltrace cost summary` keeps its flags (`--since`, `--group-by`, `--json`) and output format. Totals now cover every run in the window. No new flags.

### Go Package API

- New unexported helper `listAllCostRuns` in `package api`. No exported signatures changed.
- New package-level variable `costRunsPageSize int` in `package api` and `package petaltrace` (both default 1000), not exported beyond each binary's package.

### Configuration

N/A — no new or changed config fields.

## Usage Examples

### Example: multi-page aggregation (behavior before vs after)

With 2,500 matching runs in the window, all older than one page:

```bash
# Before: fetched a default page of 50 (10000 clamps out of range);
# reported totals for 50 runs only.
petaltrace cost summary --since 30d --json
# {"total_runs": 50, ...}

# After: totals cover all 2,500 matching runs.
petaltrace cost summary --since 30d --json
# {"total_runs": 2500, "total_tokens": ..., "total_cost": ..., ...}
```

### Example: API summary across pages

```bash
curl 'http://127.0.0.1:8090/api/cost/summary?since=2026-11-12T00:00:00Z&until=2026-11-19T00:00:00Z&group_by=workflow'
# by_workflow now includes every workflow present on any page.
```

### Example: API timeseries across pages

```bash
curl 'http://127.0.0.1:8090/api/cost/timeseries?bucket=24h&since=7d'
# Each time bucket sums every run in the window that maps to it, not just
# the runs on the first page.
```

## Integration Notes

- `ListRuns` cursor semantics (`id < cursor`) are unchanged. Callers in `api/runs.go`, `api/live.go`, `mcp/tools_prompt.go`, `mcp/tools_trace.go`, and the other CLI commands are untouched and retain their existing (page-one) semantics; converting them is out of scope for this issue.
- Known pre-existing limitation surfaced while testing (not caused or fixed here): `CostEstimate.ByProvider` and `CostEstimate.ByModel` are collector-side, in-memory aggregates and are not persisted — the stores only store `estimated_cost_usd` (Total). Consequently the CLI's "By Provider"/"By Model" groups are always empty when reading persisted runs. The API summary derives provider/model groups from persisted LLM spans (`llm_data` JSON), so those work. If provider/model CLI groups are wanted, the cost breakdowns must first be persisted — deferred separately.

## Breaking Changes & Migration

None. CLI flags, output formats, API request/response shapes, and store APIs are unchanged. The only observable behavior change is that reports now include all matching runs, which is the intended fix.

## Deferred / Out of Scope

- Persisting `CostEstimate.ByProvider`/`ByModel` (or deriving CLI provider/model groups from spans, as the API already does).
- Converting remaining single-page `ListRuns` callers (`api/runs.go`, `api/live.go`, `mcp/*`, other CLI commands) to full traversal.
- Generalizing store pagination so cursors are sort-aware for all sort columns.
