## Summary

Replay records are now stored through `TraceStore`, so replay status and identifiers are available to new engine instances and after daemon restarts. SQLite schema version 3 and PostgreSQL migration version 2 add replay tables; the engine, replay API, and CLI status/diff commands use the persisted records.

## Motivation

Replay records previously existed only in a replay engine's memory. CLI status and diff commands construct a new engine, and API servers can restart, so they could not retrieve replays created by earlier processes. Persistence makes replay IDs, source and new run IDs, mode, status, timestamps, errors, and diff IDs durable.

## What Changed

### New Additions

- `store.ReplayRecord` holds a replay's ID, source and new run IDs, diff ID, mode, status, error, start time, and optional completion time.
- `store/sqlite_replays.go` and `store/postgres_replays.go` implement create, get, update, and list operations for replay records.
- `store/sqlite_replays_test.go` and `cmd/petaltrace/replay_persistence_test.go` verify SQLite replay lifecycle and CLI persistence behavior.

### Modifications

- `store.TraceStore` now includes `CreateReplay`, `GetReplay`, `UpdateReplay`, and `ListReplays`.
- SQLite migration 3 creates `replays` with a source-run foreign key and indexes on source run and start time. PostgreSQL migration 2 creates the equivalent table and indexes.
- `replay.Engine` persists replay results, loads records from the store, refreshes status from the associated run, and persists diff IDs.
- API replay status and list handlers load persisted records. The replay engine is now scoped to each API server instance.
- CLI replay status loads from the store; CLI replay diff saves the computed diff ID to the replay record.
- SQLite connection setup now enables foreign keys with the `modernc.org/sqlite` `_pragma=foreign_keys(1)` DSN parameter.
- Test stores implement the added `TraceStore` methods.

### Removals

- The replay engine's in-memory replay map was removed. Persisted storage is now the source of replay records.

## Technical Specification

### Data Schemas / Types

```go
type ReplayRecord struct {
	ID          string     `json:"id"`
	SourceRunID string     `json:"source_run_id"`
	NewRunID    string     `json:"new_run_id,omitempty"`
	DiffID      string     `json:"diff_id,omitempty"`
	Mode        string     `json:"mode"`
	Status      string     `json:"status"`
	Error       string     `json:"error,omitempty"`
	StartedAt   time.Time  `json:"started_at"`
	CompletedAt *time.Time `json:"completed_at,omitempty"`
}
```

`TraceStore` adds these methods:

```go
CreateReplay(ctx context.Context, replay *ReplayRecord) error
GetReplay(ctx context.Context, id string) (*ReplayRecord, error)
UpdateReplay(ctx context.Context, replay *ReplayRecord) error
ListReplays(ctx context.Context, sourceRunID string) ([]ReplayRecord, error)
```

An empty `sourceRunID` lists all replay records in descending start-time and ID order. A missing ID returns `(nil, nil)` from `GetReplay`; updating an unknown ID returns an error. `CreateReplay` generates an ID and a UTC start time if those fields are empty.

SQLite migration version 3 and PostgreSQL migration version 2 create a `replays` table with columns `id`, `source_run_id`, `new_run_id`, `diff_id`, `mode`, `status`, `error_message`, `started_at`, and `completed_at`. The source run references `runs(id)` with `ON DELETE CASCADE`.

### API Endpoints

- `GET /api/replay/{id}` reads the record from the store and refreshes a running replay's status from its new run.
- `GET /api/replays?source_run_id={run_id}` lists persisted records. Omitting `source_run_id` lists all records.
- `POST /api/replay` stores the replay result before returning it.

Successful status and list responses preserve the existing `ReplayAPIResponse` fields: `replay_id`, `source_run_id`, `new_run_id`, `diff_id`, `mode`, `status`, `error`, `started_at`, and `completed_at`.

### CLI Interface

```text
petaltrace replay status <replay_id>
petaltrace replay diff <replay_id> [--include-content]
```

Both commands open the configured store and load the replay record by ID. `status` refreshes its status from the associated run. `diff` requires a completed replay with a new run ID, computes and caches the run diff, and saves its ID on the replay record.

### Go Package API

`replay.Engine` exposes store-backed lookup methods:

```go
LoadReplay(ctx context.Context, replayID string) (*Replay, error)
LoadReplays(ctx context.Context, sourceRunID string) ([]*Replay, error)
UpdateReplay(ctx context.Context, replay *Replay) error
```

`RefreshReplayStatus(ctx, replayID)` now loads the replay from storage and persists a status transition when the associated run is completed or failed. Existing convenience methods `GetReplay`, `ListReplays`, and `GetReplaysBySourceRun` remain available.

### Configuration

N/A. No user-facing configuration fields were added.

## Usage Examples

### Example: Check a replay after restarting the daemon

```sh
petaltrace replay status 123e4567-e89b-12d3-a456-426614174000
```

The command loads the replay record from the configured store. To compute and persist a diff for a completed replay:

```sh
petaltrace replay diff 123e4567-e89b-12d3-a456-426614174000 --include-content
```

An unknown replay ID returns an error such as:

```text
getting replay status: getting replay: replay not found: unknown-replay
```

## Integration Notes

Replay records are written by the replay engine using the configured `TraceStore`, allowing the CLI and API to share state across process boundaries. This does not change PetalFlow execution requests, graph IR, MCP adapter behavior, or Cortex/Iris/PetalTrace integration contracts.

## Breaking Changes & Migration

None. SQLite users receive schema version 3 through the existing migration runner. PostgreSQL users receive migration version 2 when migrations run.

## Deferred / Out of Scope

- Replay request overrides and captured execution payloads are not stored; only replay metadata and result identifiers are persisted.
- PostgreSQL persistence is limited to replay records in addition to its existing supported run/span operations; other unsupported store operations remain unchanged.
